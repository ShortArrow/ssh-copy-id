## 目的と基本方針

Windowsから接続先へ公開鍵を登録するRust製CLIを作る。既存のLinux版
`ssh-copy-id` と、引数・鍵の選択・登録済み判定・実行結果の使い勝手をできるだけ揃える。
この文書は対応済み機能の一覧ではなく、実装と検証の基準である。

- 通常はSSH経由で接続先のコマンドを実行して登録する。
- `-s` はSFTP方式を選ぶ。ACL設定や検出のためにもリモートコマンドを実行しない。
- 秘密鍵は接続先へ送らない。登録する公開鍵はコマンド文字列に埋め込まず、データとして送る。
- ホスト鍵確認と既存のSSH接続設定を尊重する。
- 鍵登録に必要なファイル操作と権限設定を扱い、サービスの起動・停止・再起動は行わない。
- 将来のAPTなどのパッケージマネージャーでの配布に向け、実行時・ビルド時の依存を最小限に保つ。

### 設計の立場

2026-09-24に記録。この文書の決定は次の4点に従う。

1. 差異を決める前に、固定した上流のスクリプトとマニュアルを読み、その動作が何を意図していると読めるかを記録する。この読み込みなしに差異は記録しない。
2. 上流と変えるのは、次のいずれかの理由があるときに限る。誤った成功・失敗の報告、ユーザーが変更を求めていないデータの破壊、秘密情報の送信、対応プラットフォームで実行できない操作。理由は差異の隣に書く。
3. Unix系とWindowsの接続先で、プラットフォームが許す限り同じ観測可能な動作にする。同じオプション、同じ結果状態、同じ終了コード、同じメッセージ。プラットフォームの制約で揃えられない箇所は、互換性の差異ではなく接続先の差異として扱う。
4. 合意した差異はすべて一覧に載せる。上流との差異は `D-xx`、接続先の差異は `O-xx` として[差異一覧](compatibility.jp.md)に置き、各行から本書の決定へリンクする。

上流の動作は中立に記述する。差異を記録しても、上流を不具合とは分類しない。

## プロジェクトのスコープ

このプロジェクトは、1回の実行につき1台の接続先の指定アカウントに、既存のSSH公開鍵を
登録する。登録に必要な鍵選択・認証確認・ファイル更新・権限設定を担当する。
置き換える対象は `ssh-copy-id` コマンドであり、OpenSSHパッケージ全体ではない。

指定アカウントは接続対象を示し、そのアカウントだけへの認証許可を保証するものではない。
Windows OpenSSHの既定の管理者用鍵ファイルは管理者アカウント間で共有される。
詳細は[Windows管理者への登録範囲](#windows管理者への登録範囲)を参照。

### 対象に含めるもの

- 以下の互換性ルールに従い、ファイルまたは利用可能なagentから既存の公開鍵を選ぶ。
- パスワードや登録済みの鍵など、既存の認証手段で接続する。初回のアクセス手段が既に存在することを前提とする。
- 選択した鍵で認証できるか確認し、残りの鍵を登録する。強制登録とdry-runも扱う。
- 必要に応じて登録先ディレクトリ・鍵ファイルを作成し、既存エントリを保持して改行を適切に補い、鍵を追記する。
- 認証したアカウントの権限と選択した通信方式の能力の範囲で、登録先の鍵ファイルとディレクトリに必要な権限を設定する。
- リモートコマンド方式とSFTP方式で登録し、結果やエラーを明確に表示する。
- 既存のSSH接続オプションの使い勝手を維持し、互換性の差を文書化する。
- 依存を最小限に保ちながら、このCLIをビルド・テスト・文書化・パッケージ化する。Linuxの既存コマンドとの共存も扱う。

### 対象に含めないもの

- 鍵ペアの生成、秘密鍵のコピー・バックアップ、証明書の発行、認証局の管理。
- 登録済みの鍵の削除・失効・ローテーション・同期。既存エントリの整理も行わない。
- SSHサーバーの導入・初期設定、`sshd_config` の変更、認証方式の有効化、ファイアウォールやアカウントの設定。
- `ssh-agent` や `sshd` の起動・停止・有効化・再起動、および鍵追加のための `ssh-add` の実行。ユーザー設定に従うSSHによる追加は、後述のagent方針で扱う。
- 自動的な権限昇格や、登録先の鍵ファイルとディレクトリ以外の権限修復。
- 汎用SSHターミナル、ファイル転送クライアント、複数ホストの集中管理、OpenSSH実行ファイル群の代替。
- SSHや暗号の独自実装、およびアクセス獲得のためのホスト鍵検証・認証の回避。

前提条件が不足する場合は問題を報告し、暗黙にシステムの初期設定まで操作を広げない。
この境界を越える機能を追加する場合は、明示的にスコープを決定し、
両言語の設計書を更新する。

## 依存と配布の方針

推移的依存、ネイティブライブラリ、外部コマンド、ビルドツールも含め、依存を小さく保ち、
必要性を説明できるようにする。単純な処理にはRust標準ライブラリを優先する。
正確性・セキュリティ・互換性・保守性に明確な利点があれば依存を追加する。
依存削減のために暗号やSSHを独自実装しない。

- 接続処理にはシステムのOpenSSHクライアントを最初に評価する。必要な実行ファイルは実行時依存として数え、明記する。外部コマンドの利用は依存ゼロではない。
- crateの追加時は、目的・推移的依存・ライセンス・保守状況・パッケージ化への影響を確認する。可能な範囲で不要なオプション機能を無効にする。
- 追加の言語ランタイム、大規模なフレームワーク、ネイティブライブラリの同梱は、文書化した必要性がある場合に限る。プラットフォーム固有の依存は対象プラットフォームに限定する。
- テスト・開発用ツールと、配布するプログラムのビルド・実行に必要な依存を分ける。
- 宣言したソースと依存を用意した後は、ネットワークアクセスなしでビルドできるようにする。ビルドスクリプトやインストール処理でツールやコードを暗黙にダウンロードしない。
- ローカルの実行時要件と、シェルや `icacls.exe` など接続先の要件を分けて記載する。

### OpenSSHパッケージとの共存

Windowsでは `ssh-copy-id.exe` として配布し、Linuxパッケージでは
`/usr/bin/ssh-copy-id-rs` としてインストールする。OpenSSHが所有する既存の
`/usr/bin/ssh-copy-id` は変更しない。Linuxのマニュアルとシェル補完も
`ssh-copy-id-rs` に合わせ、パスの衝突を避ける。

コマンド名を引き継ぐためだけに `openssh-client` や `openssh` との競合・置換を
宣言したり、それらのパッケージ全体を提供すると宣言したりしない。
接続方式にOpenSSHを選んだ場合は、必要な実行時依存として宣言する。

従来のコマンド名で使いたいユーザーは、自分のシェルで明示的に設定できる。

```sh
alias ssh-copy-id=ssh-copy-id-rs
```

パッケージがこのエイリアスを自動追加したり、ユーザーのシェル設定を自動変更したりしない。
パッケージ名は未決で、実行ファイル名と一致させる必要はない。
この方針はAPT・pacman向けパッケージやLinuxクライアント対応が既に提供されていることを意味しない。

### バージョンとリリース

2026-09-30に決定し、2026-10-01に訂正した（DL-46）。所有者のrunexとgitreantの
リポジトリに合わせる。各項目に、どちらのリポジトリに合わせたかを書く。

- 版番号はセマンティックバージョニングに従う。`Cargo.toml` は最初のリリースまで0.0.0とし、v0.0.1を含むすべてのリリースで、版番号を上げる専用のコミットを打つ。リリースは段階1の0.0.1から始め、段階1.5を0.0.2、Windows接続先に対応する段階2を0.1.0とする。0.1.0以降1.0.0までは、コマンドラインの破壊的変更でminorを、それ以外でpatchを上げる。
- ブランチはrunexと同じくトランクベースで運用する。`main` は常にリリースできる状態に保ち、変更は短命ブランチ（`feat/`、`fix/`、`docs/`、`ci/`）からプルリクエストで入れる。issueがあればブランチ名にその名前を付ける。`main` へ直接pushするのは、リリースのために版番号を上げるコミットだけとする。所有者の一般規則である「版管理するパッケージはGitFlow」はここでは適用しない。runexが `develop` を廃止したのと同じ理由で、各変更がすでに独立したプルリクエストとして入るので、統合用のブランチは修正を遅らせるだけになる。
- リリースは `main` 上の署名付き注釈付きタグ `vX.Y.Z` とし、`git tag -s` で作って `git tag -v` で確かめる。runexが現在求めている手順で、runexのv0.1.20までのタグは、注釈付きだったが署名はなかった。`v0.0.1-pre` のように `-` を含むタグは、gitreantと同じくプレリリースとし、これも署名する。プレリリースはcrates.ioへ公開せずにリリース手順を試すために使う。gitreantではタグのコミットに `[skip publish]` を書かない限り公開されるが、ここでは `-` を含むタグでは公開のジョブを必ず飛ばす。crates.ioでは一度公開した版番号を再利用できないためだ。
- `CHANGELOG.md` はrunexと同じくKeep a Changelogの形式にする。gitreantには変更履歴がない。利用者に見える変更は `[Unreleased]` に項目を足し、リリースでその見出しを版番号と日付に変える。項目には、追加・変更した差異のIDを書く。
- `release.yml` はv0.0.1の前に、runexとgitreantを元に作る。両者とも、Linux・Windows・macOSのテストを関門にし、ビルド、GitHubのリリース、OIDCによるTrusted Publishingでのcrates.ioへの公開を行う。runexと同じく、`CONTRIBUTING.md` にリリースのチェックリストを併せて書く。クレート名は `ssh-copy-id` とする。`ssh-copy-id` と `ssh-copy-id-rs` は、2026-09-30と2026-10-01にcrates.ioのAPIで404を返した。
- v0.0.1はcrates.ioとGitHubのリリースだけで公開する。runexとgitreantが使っているwingetなど、ほかの入手方法は後で決める。
- 未決: Linuxで `cargo install` すると `ssh-copy-id` という名前の実行ファイルが入り、`PATH` の順によってはOpenSSHのコマンドを隠す。Linuxパッケージで選んだ `ssh-copy-id-rs` とは食い違う。

## Linux版との互換性

### 固定した上流の比較基準

OpenSSH portableのコミット
[`eabf1987de772f0f2d772fd6bd72b4c84d0ab780`](https://github.com/openssh/openssh-portable/commit/eabf1987de772f0f2d772fd6bd72b4c84d0ab780)
を互換性の比較基準とする。上流の `master` を `git ls-remote` で照会して取得した。
参照するファイルは
[`contrib/ssh-copy-id`](https://github.com/openssh/openssh-portable/blob/eabf1987de772f0f2d772fd6bd72b4c84d0ab780/contrib/ssh-copy-id)と
[そのマニュアル](https://github.com/openssh/openssh-portable/blob/eabf1987de772f0f2d772fd6bd72b4c84d0ab780/contrib/ssh-copy-id.1)とする。

引数の解釈・終了コード・出力内容を、この固定した版と比較する。
合意済みの差異は上流の動作を再現せず、本プロジェクトの設計どおりにテストする。
Ubuntuなどのディストリビューション固有のパッチへの追従は別途判断し、
自動的に比較基準を変更しない。上流の更新は内容を確認してから、参照コミットと
影響を受けるテストを明示的に更新する。

コミットIDは固定済みで、この版に対する登録対象の鍵の限定実験は成功した。
互換性テスト全体はまだ実装していない。
以下は互換性の目標であり、完全互換を宣言するものではない。

### CLIの互換性目標

| 操作・引数 | 目標とする振る舞い |
| --- | --- |
| `[user@]host` | SSH設定のホスト別名も含めて接続先として扱う |
| `-i [identity_file]` | 指定した公開鍵を選ぶ。`.pub` がなければ補う。引数省略時の解析も上流に合わせる |
| `-i` 未指定 | agentの公開鍵を優先し、なければ `~/.ssh/id*.pub` の最新更新ファイルを選ぶ。`*-cert.pub` は除外 |
| `-p port` | 接続先ポート |
| `-o option`、`-F config` | SSHのオプション・設定ファイル。`-o` は複数指定可能 |
| `-f` | 登録済み確認を省略する。公開鍵のみでも登録可能で、重複が生じ得る |
| `-n` | 登録予定の鍵を表示し、登録処理は行わない。`-f` で省略しない限り、登録済み確認のために接続する |
| `-s` | SFTPで登録する |
| `-t target_path` | 接続先の登録ファイルを指定する |
| `-h`、`-?` | ヘルプを表示する |

通常の登録済み判定は、その鍵で認証できるかを基準とする。
`authorized_keys` の文字列一致に置き換えない。対象外の鍵や既存の多重化接続で
認証が成功し、誤って登録済みと判定されないようにする。
接続失敗やホスト鍵エラーを「未登録」として処理しない。

### 記録する差異: 登録済み確認に使われた鍵

2026-09-20の決定: 上流の動作を不具合、本プロジェクトの変更を不具合修正とは分類せず、
既存版との動作の差異として記録する。元の設計者の意図は確認が取れていない。

読み取った意図（2026-09-24記録）: 上流の確認接続は「この鍵でログインできるか」を
安価に試すもので、`-i` の鍵がクライアントの提示する唯一の鍵だという前提に立って
いる。確認接続で `IdentitiesOnly=yes` を付けているのがその根拠になる。設定された
`IdentityFile` が加算されるため、この前提は成り立たない。変える理由: 誤った成功報告。

確認した上流ソースでは、確認用接続が成功すると登録対象の鍵をスキップし、
実際にどの鍵で認証したかをスクリプト側で個別に検証していない。
設定された別の鍵が認証候補に残る場合がある。本プロジェクトでは、別の鍵による
認証成功を、登録対象の鍵が登録済みである根拠にしない。
実際の登録操作への接続に、既存の別の鍵を使うことは認める。

2026-09-24の決定: 確認の結果は3つに分ける。

| 結果 | 条件 | 扱い |
| --- | --- | --- |
| 登録済み | クライアントが提示できる候補が登録対象の鍵だけで、確認接続が成功した | 登録をスキップする |
| 未登録 | 候補が登録対象の鍵だけで、サーバーが `Permission denied` を返した | 登録する |
| 不確定 | 別の鍵や証明書も候補だった、認証後にセッションが失敗した、その他のエラーが出た | 理由を表示して登録する。`-f` と同様に重複が生じ得る |

候補が他にあるかは `ssh -G` の出力で判定する。Linux実験で行った、登録対象の鍵だけを
含む設定の生成は、不確定を減らす最適化として後回しにする。最初の2つの到達点では
必須にしない。このケースはDockerで再現確認済み。
詳細は[登録対象の鍵を限定する実験結果](#登録対象の鍵を限定する実験結果)を参照。

### 記録する差異: SFTP方式の登録済み確認

2026-09-20の決定: 通常モードは既存版と同様にリモートの `exit` で確認する。
`-s` では登録対象の鍵でSFTPセッションを確立して確認し、`exit` を含め
リモートコマンドを送らない。単なるTCP接続ではなく、SFTPプロトコルのセッション成立を必要とする。

確認した既存版は `-s` でも `exit` を試行し、
`allows sftp connections only` というメッセージも確認成功として扱う。
本プロジェクトでは、このメッセージをSFTPセッション成立の代替判定に使わない。
不具合修正とは分類せず、設計差異として記録する。

読み取った意図（2026-09-24記録）: このメッセージ判定は、SFTPしか許可しない
サーバーで `exit` が成功し得ないことへの対応と読める。変える理由: 誤った成功報告。
メッセージはシェルが拒否されたことしか示さず、その鍵でSFTPセッションが開けたことを
示さない。

両モードに前述の登録対象の鍵に関する判定方針を適用する。`-f` は確認を省略する。
SFTPセッションを確立できないことだけで鍵が未登録とは判断しない。
認証拒否とその他の失敗を区別する実現方法は未決とする。
今回の決定は、通常モードの終了コードによる確認を認証結果の直接取得へ
全面的に置き換えるものではない。

### 記録する差異: 任意の登録先の既存親ディレクトリ

2026-09-20の決定: `-t` で登録先を指定した場合、通常モード・SFTPモードの両方で、
既存の親ディレクトリの権限を変更しない。権限不足で登録できなければ、
親ディレクトリのモードやACLを変更せず、エラーを報告する。

確認した既存版の通常モードは、新規作成に `umask 077` を使い、既存の親に
一律のchmodは行わない。SFTPモードは親ディレクトリを700に設定する。
本プロジェクトのSFTPモードで既存の親の権限を保持することを、不具合修正ではなく
設計差異として記録する。

読み取った意図（2026-09-24記録）: SFTPモードのchmodは、SFTPでは表現できない
`umask 077` の代わりであり、新規作成した `~/.ssh` を想定したものと読める。
変える理由: `-t` が共有ディレクトリを指すとき、ユーザーが変更を求めていない
データを壊す。

今回の決定対象は、`-t` で指定した登録先の既存の親ディレクトリとする。
残りは2026-09-24に決定した。新規作成するディレクトリと鍵ファイルは上流に従う。
通常方式は `umask 077`、`-s` は本ツールが作成したディレクトリに `chmod 700`、
鍵ファイルに `chmod 600` を行う。既存ファイルのモードは通常方式では変えず、`-s` は
上流と同じくアップロードした鍵ファイルに `chmod 600` を行う。リンクは上流と同じく
辿り、リンクや再解析ポイントの検査は追加しない。信頼境界はアカウント自身のホーム
ディレクトリで、同時のリンク差し替えはその外にある。`-t` のパスは、Unixの
スクリプトにはPOSIXの単一引用符エスケープで、Windowsのスクリプトには
PowerShellの単一引用符リテラルとして埋め込む。パス中の引用符はデータになる。
上流はパスを単一引用符で囲んだ `sh -c` の引数の中に埋め込む。そのためパスに
引用符があるとスクリプトの文字列がそこで終わり、パスの残りがシェルの構文として
読まれる。読み取った意図: `-t` はホームからの相対の単純なパスを指定するもの。
変える理由: 実行が失敗するか、パスの文字列がそのアカウントでコマンドとして
実行される。ユーザーが変更を求めていないデータを壊し得る。差異D-11として記録する。
共有ディレクトリ内の任意パスをテストし、権限不足で登録に失敗する場合も含め、
両モードで親の権限が変更されないことを確認する。

2026-09-30の決定: 相対パスの `-t` は、上流と同じくホームからの相対とする。上流は
書き込み前に `cd` する。Windows接続先ではプロファイルからの相対とする。
通常方式の同時登録は、上流の `cat >>` と同じく追記に任せ、ロックは加えない。
どちらも差異ではない。

### その他の互換性に関する未決事項

2026-09-24の決定: 終了コードは上流と同じ0と1にする。usageエラーも1とする。
対応は[登録結果](#登録結果)に書く。残りも2026-09-24に決定した。メッセージは
共通の動作については上流の文言に合わせ、ゴールデンテストで比べる。`-x` は
各クライアントコマンドとリモートスクリプトを実行前にstderrへ出力する。上流の
`set -x` に最も近い動作になる。上流の `-x` の読み取った意図: シェルスクリプト
自体をトレースすること。変える理由: コンパイルしたプログラムにはシェルの
トレースがなく、プラットフォームとして同じ動作ができない。差異D-14として記録する。
出力の形は違うが、目的は同じ。上流の特例は残す。OpenWrtでrootなら
`/etc/dropbear/authorized_keys` に、Haikuでは `config/settings/ssh/authorized_keys` に
登録し、NetScreenでは上流と同じく鍵1本ごとにコマンドを送る。
書き込み失敗を成功扱いしない。

### dry-runの動作

`-n` は登録済み確認を行い、登録予定の鍵を表示する。
登録先ディレクトリ・鍵ファイルの作成、鍵の追記、それらの権限変更は行わない。
`-f` で確認を省略しない限り、そのための接続は行う。接続に伴う認証ログ、
ログインフック、ホスト鍵の処理、ユーザー設定の `AddKeysToAgent` による動作は発生し得る。

ヘルプでは「登録予定の鍵を表示し、登録処理は行わない」と説明し、
オフライン動作や副作用が一切ない動作とは説明しない。
これは既存版のdry-runの範囲を明確にするもので、新たな動作差異にはしない。
別途記録したSFTP方式の確認方法の差異は適用する。
2026-09-24の決定: `-n -f` は接続しない。上流でも `-f` は確認接続の処理を通らない。

## 処理の流れ

1. 引数を解析し、鍵と接続設定を選ぶ。
2. `-f` 以外では鍵ごとに認証を確認し、登録済みの鍵を除く。
3. 全鍵が登録済みなら正常終了する。`-n` なら予定を表示して終了する。
4. 通常方式では、`--target-os` が無ければ接続先のシェル系統を判定する。判定できなければ書き込み前に止める。
5. 登録先と必要な権限処理を決定する。
6. 既存内容を保持し、末尾改行を必要に応じて補って公開鍵を追記する。
7. 結果行を読み取り、結果を表示する。
8. `-f` 以外では、書き込んだ鍵ごとに認証できるか確認し、登録したが未検証の鍵を報告する。

### 登録結果

2026-09-24の決定: 1回の実行の結果は4つのいずれかとし、上流と同じ2つの終了コードに
対応させる。

| 結果 | 意味 | 終了コード |
| --- | --- | --- |
| 変更なし | 何も書いていない。全鍵が登録済み、dry-runで終了、または最初の書き込み前に停止 | 登録済み・dry-runは0。エラーで停止した場合は1 |
| 登録済み | 選択した鍵をすべて追記し、ファイルを閉じた | 0 |
| 部分書き込み | 一部を書いた後、既知の段階で失敗した | 1 |
| 不明 | 結果行を受け取らずに接続が終わった | 1 |

接続先の登録スクリプトは結果行を出力し、CLIはこの行だけから結果を決める。
書式は2026-09-30に決定した。鍵ごとに
`ssh-copy-id: key=<n> result=<added|skipped|failed> path=<ファイル>` を1行出し、
最後の出力として総括の `ssh-copy-id: result=<unchanged|installed|partial> added=<n>` を
1行出す。`<n>` は入力の中の鍵の順番で、1から数え、先頭に0を付けない。`<ファイル>` では、
`0x21`〜`0x7E` の範囲外のバイトと `%`・`=` を、大文字16進の `%XX` で書く
（DL-39で `0x80` 以上を加えた。コンソールのコードページで非ASCIIのパスが化けないようにするため）。
`ssh-copy-id: ` で始まらない行は無視する。この接頭辞を持つ行が解釈できない場合
（UTF-8でない場合を含む）や、総括の後に接頭辞付きの行がある場合は不明とする。鍵ごとの行があるので、
部分書き込みの前にどの鍵まで書けたかが分かる。これらの行はユーザーには見せず、
ユーザーには上流と同じメッセージを出す（DL-26）。接続先の終了コードは使わない。
Windowsの既定シェルが終了コードを置き換えるためで、記録は
[接続先の差異](compatibility.jp.md#接続先の差異)のO-04と
[W05の測定（英語）](validation.md#command-delivery-and-exit-codes)にある。
結果行がなければ不明とする。usageエラーは上流と同じく1で終了する。

### 記録する差異: 登録後の検証

2026-09-24の決定: 鍵を書き込んだ後、通常方式と `-s` の両方で、`-f` が無い限り
書き込んだ鍵ごとに登録済み確認をもう一度行う。各鍵を「登録し検証済み」か
「登録したが未検証」（理由付き）として報告する。検証で拒否されても終了コードは
変えない。ファイルは書けているので、次に確認すべき箇所（管理者の共有ファイル、
ファイルのACLなど）をメッセージで伝える。

確認した既存版は書き込み後に検証せず、ログインコマンドの例を表示する。
読み取った意図: 検証はユーザーの次のログインに任せる。Unixでは `umask 077` が
`StrictModes` を満たすので、それで足りることが多い。変える理由: 誤った成功報告。
Windows接続先では、ACLの不備、プロファイル未作成、既定設定で管理者の個人ファイルが
無視される場合に、鍵は黙って拒否される。そのため本プロジェクトは検証する。
不具合修正ではなく差異D-06として記録する。検証には登録対象の鍵の確認と同じ
3つの結果を使い、不確定なら「未検証」と報告する。

### 公開鍵入力

`restrict`・`command=` などの鍵オプションとコメントを保持する。
鍵の種類と鍵データだけから登録する行を再構成しない。
以下の合意済みの差異は、`-f` を含め両方の登録方式に適用する。
これは設計上の決定であり、実装済み・検証済みではない。

#### 秘密鍵入力の拒否

確認した既存版には、登録用入力に含まれる秘密鍵の内容を明示的に拒否する処理がなく、
`-f` ではその内容が送信され得る。本プロジェクトでは、公開鍵の登録用入力として
渡された秘密鍵の内容を、その入力を送信する前に拒否し、エラーにする。
`-f` が省略するのは登録済み確認であり、この入力確認は省略しない。
認証のためにSSHがローカルの秘密鍵を使うことは禁止しない。

読み取った意図（2026-09-24記録）: 上流は呼び出し側が `.pub` ファイルか
`ssh-add -L` の出力を渡す前提で、公開鍵だけで済むように `-f` がある。
変える理由: 秘密情報の送信。

検出方法は2026-09-24に決定した。`-----BEGIN` に続いて `PRIVATE KEY` を含む行が
1行でもあれば入力全体を拒否する。OpenSSH、PKCS#8、PKCS#1のRSA、EC、DSA、
暗号化された各形式はこのアーマーを共有する。OpenSSH・PEMの代表的な秘密鍵入力、
公開鍵と秘密鍵が混在する入力、強制モードを含め、内容が送信されないことを検証する。

#### CRLFの正規化

確認した既存版には、CRLF入力からCRを明示的に除去する処理がない。
本プロジェクトでは、送信する公開鍵の登録用入力の改行をCRLFからLFへ変換する。
鍵オプションとコメントを保持し、接続先の既存内容やローカルの入力元ファイルは変換しない。
両方の登録方式と強制モードで、制限付きの行・コメントを含むLFとCRLFの入力を検証する。

読み取った意図（2026-09-24記録）: 上流のスクリプトは同じUnixホストで作られた入力を
想定していて、CRLFは現れない。変える理由: 誤った成功報告。CRで終わる行は鍵として
使えない。

今回の決定で厳密な公開鍵パーサーは採用しない。不正入力は2026-09-24に決定した。
単独のCR、NULバイト、空行でも `#` コメントでも鍵の行でもない行は、行番号を付けて
送信前に拒否する。メモリ以外のサイズ上限は設けない。文字コードはバイト列のまま
通す。先頭のBOMは次項で扱う。
鍵の行の定義は2026-09-30に決定した。先頭の空白・タブの後が
`[オプション] 鍵の種類 base64 [コメント]` の形をした行とする。鍵の種類は `ssh-`・
`ecdsa-sha2-`・`sk-ssh-`・`sk-ecdsa-sha2-` のいずれかで始まり、証明書の種類も含む。
base64の欄は `A-Z a-z 0-9 + /` が1文字以上続き、その後に `=` が2個まで付く。
オプションは最初の欄が鍵の種類でない場合だけあり、ダブルクォートの外の最初の
空白かタブで終わる。クォート内の `\"` はエスケープしたクォートとする。上流はこうした行も追記する。読み取った意図: 入力は
`ssh-keygen` か `ssh-add` の出力で、形式は正しい。変える理由: 誤った成功報告。
上流が登録済みと数えた不正な行を、sshdは無視する。差異D-10として記録する。

証明書は2026-09-30に決定した。種類が `-cert-v01@openssh.com` で終わる証明書の行と
`cert-authority` の行は、上流と同じくそのまま通す。sshdは鍵ファイル内の証明書の行を
ログインに使わないので、登録済み確認と登録後の検証は、その理由を付けて不確定と
報告する。差異は記録しない。

#### 先頭のBOMの除去

2026-09-24の決定: 登録用入力の先頭にあるUTF-8のBOMを、送信前に取り除く。
対象は入力の先頭3バイトだけで、接続先の既存内容とローカルの入力元ファイルは変更しない。
読み取った意図: 上流は `ssh-keygen` か `ssh-add` が書いた入力を想定していて、
どちらもBOMを出力しない。変える理由: 誤った成功報告。BOMで始まる行は鍵として
認識されない。WindowsのエディタやPowerShell 5のリダイレクトはこの形のファイルを作る。
不具合修正ではなく差異D-07として記録する。BOM付きの `.pub` を両方の登録方式と
強制モードで検証する。

## 接続先OSとシェル

最初にUnix系接続先への基本経路を実装し、Windows接続先へ拡張する。
OS指定は通常操作で必須にせず、既定はLinux版同様のUnix系接続先を想定する。

| 接続先 | 通常の登録先 | 権限の扱い |
| --- | --- | --- |
| Unix系 | `.ssh/authorized_keys` | ディレクトリ700・ファイル600を基本に、既存権限の扱いを上流と比較して決める |
| Windowsの一般ユーザー | ユーザープロファイル内の `.ssh/authorized_keys` | ユーザー用ファイルのACL要件に合わせる |
| Windowsの管理者グループ所属ユーザー | 既定設定では `%ProgramData%/ssh/administrators_authorized_keys` | SYSTEMとAdministratorsにアクセスを限定する |

登録先はサーバー設定で変更され得る。OSだけでは管理者所属や実際の登録先を
確定できない。`-t` による明示指定を尊重し、管理者用登録先の選択方法は別途決める。

SSHがコマンドを最初に解釈させる既定シェルと、登録スクリプトを実行するシェルを区別する。
例えば `SSH → cmd.exe → powershell.exe → 登録処理` という構成がある。

- Unix系の登録処理はPOSIX `sh` を基本とし、Bash固有機能を必要としない。
- Windowsの登録処理はWindows PowerShellを基本候補とし、`pwsh` との共通動作を検証する。
- `cmd` からの起動も検証対象とする。登録処理すべてをバッチ構文で実装するとは限らない。
- Linux上の `pwsh` などもあるため、シェル名からOSを決めつけない。
- 2026-09-24の決定: 通常方式では書き込み前に、POSIX `sh`・`cmd.exe`・PowerShellで出力が異なる1コマンドを送り、接続先のシェル系統を判定する。どれにも一致しなければ、何も書かずにエラーで止める。`--target-os` は判定を上書きする。`-s` はこの判定ができないため、`--target-os` が無ければUnix系を想定する。`--remote-shell` は採用しない。上流は確認せずに `sh` スクリプトを送る。読み取った意図: 接続先はPOSIXシェルを持つ。変える理由: Windows接続先ではそのスクリプトを実行できない。差異D-12として記録する。通常方式では接続が1回増え、`--target-os` という新しいオプションが加わる。2026-09-30の決定: `--target-os` の値は `unix` と `windows` の2つとする。判定コマンドとその期待出力は、`cmd.exe`・Windows PowerShell・`pwsh`・`sh`・`bash`・`dash` での実測（検証項目W09）で固定する。最初の候補は `echo %OS%:$0`。

### Windows向けのリモートコマンド

2026-09-24の決定: Windows接続先へ送るコマンドは
`powershell.exe -NoProfile -NonInteractive -EncodedCommand <base64>` だけとする。
英数字とbase64しか含まないので、`cmd.exe /c`、`powershell.exe -c`、`pwsh -c` の
どれで包まれても同じに解釈される。登録先パスを含むすべてのパラメータは
エンコードしたスクリプトの内側に置き、公開鍵は標準入力で渡す。
接続先の実行時要件として `powershell.exe` と、ACLを設定する場合の `icacls.exe` を
文書化する。`pwsh` しかない接続先への対応はW06の結果で決める。
既定シェルごとに実測したコマンド行は[検証記録（英語）](validation.md#command-delivery-and-exit-codes)にある。

## Windowsの権限とサービス

### Windows管理者への登録範囲

Windows OpenSSHの鍵ファイル設定に従う。共有の `administrators_authorized_keys` に
登録する場合は、書き込み前に登録先パスと、管理者アカウント間で共有されることを表示する。
指定アカウントだけにアクセスを許可する操作とは説明しない。

管理者アカウントごとに鍵ファイルを分離するためのサーバー設定変更は行わない。
これはLinux版との動作差異ではなく、Windows接続先の対応仕様として扱う。
2026-09-24の決定: 通常方式では、アカウントがAdministratorsグループ
（SID `S-1-5-32-544`）に属するかを接続先に問い合わせ、属していれば共有ファイルを
選ぶ。上流と同じく `sshd_config` は読まない。独自の `AuthorizedKeysFile` は `-t` で
指定された場合だけ従い、食い違いは登録後の検証（D-06）が報告する。
ACLの手順は[権限とサービスの操作範囲](#権限とサービスの操作範囲)に書く。

共有ファイルへの登録時に、書き込み前にパスと共有範囲が表示されること、
サーバー設定が変更されないこと、一般ユーザーの鍵ファイルへの登録と区別されることを検証する。

### 権限とサービスの操作範囲

2026-09-24の決定: 上流のUnix版と同じ規則にする。上流は `umask 077` で新規作成分だけを
絞る。本ツールが作成したディレクトリと鍵ファイルには、Windows OpenSSHが受け入れる
最小のACLを設定する。継承を外し、所有者をそのアカウントにし、アカウント・SYSTEM・
Administratorsにフルコントロールを与える。設定は `icacls.exe` にSIDを渡して行い、
終了コードを確認する。既存のディレクトリとファイルは、余分なエントリがあっても
ACLを変更しない。その後サーバーが鍵を拒否した場合は、登録後の検証（D-06）が
ファイルのエントリを列挙して報告し、何を外すかはユーザーが決める。
W07では先に、継承されたACLだけでサーバーの検査を通るかを確認する。通るなら、
プロファイル配下では明示的なACL設定が不要になる。
権限不足の場合は失敗を説明し、自動的な昇格やサービス操作は行わない。

`ssh-agent` は秘密鍵を扱う補助サービスであり、接続先の公開鍵登録に起動・再起動は不要。
ローカルでもagentを自動起動せず、利用できない場合は鍵ファイル選択へ進む。
`authorized_keys` の更新のみで `sshd` を再起動しない。

## agentの利用とユーザー設定

本CLIは鍵追加のために `ssh-add` を実行しない。公開鍵を列挙する `ssh-add -L` は
引き続き対象に含める。ユーザーの `AddKeysToAgent` 設定を尊重し、認証時にSSHが
鍵を追加することを防ぐ目的で上書きしない。これは確認した既存版の動作を維持する方針であり、
差異一覧には追加しない。本ツールによるagentサービスの起動・停止・再起動は行わない。

設定された `AddKeysToAgent` の動作が維持され、本CLI自身が鍵追加やサービス操作の
コマンドを発行しないことを検証する。

オプションの優先順位は2026-09-24に決定した。上流と同じ3つの段階で、上流と同じ
上書きだけを行う。

| 段階 | 本ツールが設定するオプション | ユーザーのオプション |
| --- | --- | --- |
| 登録済み確認 | `ControlPath=none`、`LogLevel=INFO`、`PreferredAuthentications=publickey`、`IdentitiesOnly=yes`、登録対象の鍵の `-i` | `-o`・`-F`・`-p` とユーザーの設定を、上書きの後ろに渡す |
| 登録 | なし | そのまま渡す |
| `-s` の転送 | 上流と同じく、`sftp` セッションで共有する制御用の接続 | そのまま渡す |

agentは、SSHクライアントが `SSH_AUTH_SOCK` と `IdentityAgent` から選ぶものを使う。
`ssh-add -L` は `SSH_AUTH_SOCK` しか見ないので、ホスト別の `IdentityAgent` があると
一覧が食い違う。上流と同じ動作なので、直さずに文書化する。

## SFTP方式

SFTP v3には `SSH_FXF_APPEND` がある。追記に対応するAPIを使う場合は、
既存内容を切り捨てる `TRUNC` を指定しない。
OpenSSHの `sftp` コマンドの `put -a` は転送再開であり、追加分だけを渡す追記操作ではない。
上流の `-s` は取得・ローカル編集・再アップロード方式である。

- ファイル不存在と、権限不足・通信失敗を区別する。2026-09-24の決定: `get` の前に登録先へ `ls -l` を実行する。上流の `-get` はすべてのエラーを無視するので区別できない。「No such file」なら不存在、それ以外のエラーなら書き込み前に止める。先頭の `-` の読み取った意図: 初回登録でファイルが無いことを許すため。変える理由: 上流は別の理由で `get` に失敗しても処理を続け、新しい鍵だけのファイルをアップロードする。既存のファイルがそれで置き換わり得る。ユーザーが変更を求めていないデータの破壊にあたる。差異D-09として記録する。
- 2026-09-24の決定: `-s` は上流と同じく全体を取得し、ローカルで編集して再アップロードする。`sftp.exe` は追記できない（DL-12）。
- 全体の書き戻しには同時更新消失の問題がある。直接追記でも重複確認・改行補完を含む
  一連の操作の原子性は保証されない。競合時の対応範囲を検証して決める。
- SFTP v3のUnix権限属性だけではWindowsのACLを適切に設定できない。
  WindowsへのSFTP登録は既存ACLなどの条件を明記し、対応範囲を限定する。
- `-s` で権限を整えられない場合に、リモートコマンド方式へ自動切り替えしない。

### 記録する差異: アップロード前の変更確認

2026-09-24の決定: `-s` では `put` の直前に登録先へもう一度 `ls -l` を実行し、
`get` の前に読んだ値とサイズか更新時刻が違えば、書かずに「変更なし」の結果と
終了コード1で止める。読み取った意図: 上流の取得・編集・再アップロードは、
書き手が1人であることを前提にしている。変える理由: ユーザーが変更を求めていない
データの破壊。`get` と `put` の間に他者が追記した行は上書きされる。
これは確認であってロックではない。2回目の `ls -l` と `put` の間の変更は
上書きされる。不具合修正ではなく差異D-08として記録する。
2回の転送の間に追記を差し込んで検証する。
- 2026-09-24の決定: Windows接続先の `-s` は、Unixと同じ既定であるプロファイル配下の `.ssh/authorized_keys` に書く。ACLを設定できず、管理者かどうかも分からないため、正しいACLのディレクトリが既にあることを前提条件とする。その後拒否された鍵は登録後の検証（D-06）が報告し、共有の管理者ファイルへの `-t` 指定か通常方式を案内する。

## 実装の分割と未決事項

### 認証時の対話

パスワードと秘密鍵のパスフレーズの入力はSSHクライアントに任せ、agentの確認要求は
SSHとagentに任せる。本CLIはパスワードやパスフレーズを収集・保存しない。
これは既存版と同じ方針であり、互換性の差異には追加しない。

Windowsで `ssh.exe` を子プロセスとして使い、公開鍵を標準入力で送りながら認証の対話が
成立することを試作で確認する。パスワード認証、暗号化された秘密鍵、agentの確認要求、
キャンセル、対話端末がない場合を対象とする。認証の対話と公開鍵のデータ経路を分け、
本CLIで認証情報を収集したり、一律に `BatchMode=yes` を指定したりして解決しない。
これは構成が成立するかの検証であり、実装済みの対応を示すものではない。

### 接続方式の評価

CLI・鍵選択・登録済み確認・接続・登録先ポリシー・ファイル更新を分離する。
上記の依存方針に従い、システムのOpenSSHクライアントから評価を始め、
次の接続方式を小さな試作で比較する。

| 候補 | 確認事項 |
| --- | --- |
| Rustから `ssh.exe` を呼ぶ | 既存SSH設定と認証を利用できる。対話入力と公開鍵送信を両立する |
| RustのSSH/SFTPライブラリ | 本CLIで認証情報を収集せず、合意した認証委譲の方針を満たせる場合に限り再検討する。SSH config、agent、踏み台、ホスト鍵検証も確認する |
| `ssh.exe` のSFTPサブシステムとRustのSFTP実装を組み合わせる | SSH側の互換性を保ちつつ、SFTP通信を扱えるか確認する |

2026-09-24の決定: 最初の2つの到達点では、システムの `ssh.exe` を起動し、`-s` では
`sftp.exe` を使う。認証結果はクライアントの終了コードと、少数のstderrパターンで
分類する。各パターンは、リリースが試験済みとして挙げるクライアントの各バージョンで試験する。2026-09-30にDL-44で変更した。一覧にない
バージョンにはエラーではなく警告を出す。詳しくは次の段落に書く。
RustのSFTP実装は `-s` の追記のためだけに再検討する。
SSHプロトコル自体を独自実装する方針ではない。

2026-09-30の決定で、同日に見直した（DL-44）。試験済みのクライアントは
`OpenSSH_for_Windows_9.5p2` と、Ubuntu 24.04のOpenSSH `9.6p1` で、どちらも既存の
検証環境で使っている。最初のパターンは `Permission denied`、ホスト鍵検証の失敗、
接続失敗の3つ。それ以外のバージョンのクライアントでは、警告を出して続ける。
既知のパターンに当てはまらない出力は確認結果を不確定にするので、鍵は警告付きで
登録され、登録後の検証が結果を報告する。バージョンは検証環境で合格してから
試験済みに加える。上流はどのクライアントでも動く。読み取った意図: 分類は
終了コードと `Permission denied` の照合1つだけなので、バージョンの一覧が要らない。
変える理由: 試験していないパターンは分類を誤り得る。誤った成功・失敗の報告にあたる。
警告と不確定の結果でその報告を防ぎ、Git for Windowsのクライアントなども拒否しない。
差異D-13として記録する。
選定時は互換性・認証動作に加え、パッケージ化の負担を含むビルド時・実行時の依存全体を比較する。

### 登録対象の鍵を限定する実験結果

[再実行可能なDocker実験](../tests/prototypes/identity-isolation/README.md)で、
Ubuntu 24.04とLinux OpenSSH `9.6p1 Ubuntu-3ubuntu13.19` を使った14項目が成功した。
実行したのは固定済みコミットの上流スクリプトで、そのSHA-256は
`a331afd275d386fd1a699e42fa1514699cf86c744ef62df3e5240d89e1443650`。
固定版スクリプトとUbuntuのSSH実行ファイルを組み合わせた検証であり、
固定コミットのOpenSSH全体をビルドした検証ではない。

| 条件 | 観測した結果（直接接続・踏み台1台経由の両方） |
| --- | --- |
| Aだけ登録済み、登録対象はB、クライアント設定にAがある | 既存版は終了コード0で全鍵スキップを報告し、Bを登録しなかった |
| 生成した設定にはBのみを指定し、Bは未登録 | 確認接続は終了コード255、`Permission denied` で拒否された |
| 接続先の登録済み鍵にBを追加 | 同じ設定で確認接続が成功した |
| 踏み台の信頼を残し、接続先のホスト鍵だけを既知のホスト鍵から除去 | ホスト鍵検証で接続が拒否された |

試作は `ssh -G` で設定を評価し、加算される鍵・証明書の一覧を除いて、
Bだけを指定した一時的な `-F` 設定を作る。踏み台1台のテストではProxyJumpを、
元の設定を読む別の `ssh -W` プロセスに置き換え、踏み台専用の鍵を維持した。
サーバーログでも、テスト中のA・Bそれぞれによる認証成功を確認した。

これはテスト条件下での実現可能性の確認であり、製品実装ではない。
接続先へのagent利用は、この実験に限って無効にしている。
任意の設定の再出力、`Match`、パーセント展開、引用符を含むパス、複数の踏み台、
証明書、agentの選択、接続多重化は引き続き検証が必要。
WindowsのSSHクライアントと対話認証は未検証で、Windows接続先の環境は後述の方針で用意する。
この結果だけで接続方式を確定しない。Dockerイメージはローカルのテスト成果物として残し、
実行ごとにコンテナと生成した鍵を削除する。

## 最初の検証項目

最初の実装単位は「明示した1本の鍵をUnix系接続先へ登録でき、再実行時に増えない」とする。
以下を振る舞いのテストに落とす。2026-09-30の決定: 最初の到達点が対象にするのは
項目1・2・3・7・8とする。項目4・5は[提供計画](#提供計画)の段階1.5、項目6は段階3で扱う。

1. 対象鍵で認証できる場合は追記せず、別の鍵での成功を誤認しない。
2. 空ファイル・存在しないファイル・末尾改行のないファイルへ正しく追記する。
3. 権限不足や通信エラーをファイル不存在と扱わず、既存内容を保持する。
4. `-n` は登録先ディレクトリ・鍵ファイルの作成、鍵の追記、それらの権限変更を行わない。`-f` で省略しない限り登録済み確認を行い、通常の接続に伴う副作用まで存在しないと説明しないことを確認する。
5. `-f` は登録済み確認を省略し、対応する秘密鍵ファイルを要求しない。
6. `-s` は検出・認証確認・ACL設定を含め、リモートコマンドを実行しない。
7. 空白・日本語・引用符を含むパスや鍵コメントをデータとして扱う。
8. 認証失敗・ホスト鍵不一致・書き込み失敗・権限設定失敗を成功扱いしない。

2026-09-24のテスト構成の決定: 引数解析、鍵入力の検証（D-04・D-05）、登録計画、
結果状態は純粋関数にして単体テストする。`ssh.exe` と `sftp.exe` の呼び出しは
バックエンドのtraitの背後に置き、偽物でCLI全体をテストする。統合テストは実物の
バックエンドで[LinuxのDocker環境](../tests/prototypes/identity-isolation/README.md)と
[Windowsのdockur環境](../tests/environments/windows/README.md)に対して行う。
互換性はゴールデンテストとし、固定した上流スクリプトと本CLIを同じLinux環境で
実行して、共通の動作について標準出力と終了コードを比べる。

CIは、変更ごとにGitHubホストのランナーで単体テストとLinux環境を実行する。
併せてLinuxで `cargo fmt --check` と `cargo clippy -D warnings` を、LinuxとWindowsで
`cargo test` を実行する。ワークフローは `.github/workflows/ci.yml` にある。
Windows環境はKVMと数GBのゲストディスクが要るため、後日用意する自前ランナーで
`workflow_dispatch` からだけ実行し、フォークからのプルリクエストは到達させない。
準備済みディスクをホストランナーへ配布する案は、評価版イメージの再配布条件を
確認するまで保留する。

検証環境の結果と未検証項目は[検証記録（英語）](validation.md)にある。
検証環境のテストはOpenSSHの動作を示すものであり、Rust CLIの適合確認ではない。
これらは開発用ツールで、製品の実行時依存には含めない。Windows対応は一般ユーザー・
管理者を `cmd`・Windows PowerShell・`pwsh` の既定シェルで検証し、SFTP専用サーバーは
別に検証する。
